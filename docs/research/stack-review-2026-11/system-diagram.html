wallpapi: how I understand the system

A UML-style component view, to check we agree. Today is the app as it is on main. Heading towards is the idea we've talked about but not specified: a desktop program that also manages the wallpaper. Hover over a component for detail; click one to trace what connects to it, and click the background to reset. Solid borders exist, dashed are planned next, dotted are planned later.

One Python process, bound to 127.0.0.1, single worker. compose.py builds every module over one SQLite file and the web layer, the workflows and three background loops use what it builds. taste/ is pure: data in, data out, no I/O. The Library is a folder that Windows' own slideshow rotates through; wallpapi never touches the desktop.

Today's app becomes the "taste core" inside a tray program. Qt owns the main thread; the server and the loops (today's three, plus a new rotator) run on threads. The core decides screen → wallpaper and crops each image to its screen; a small Desktop interface hides the operating system, with one thin adapter per platform. Windows first, the others later, and a fake for tests.

What I'm assuming about where it's heading. Correct anything that's wrong.

  • The rotation source is the Library, meaning your Favourites. Should Likes count too, or a separate "rotation set"?
  • The journey orders the whole rotation set once (nearest-neighbour then 2-opt over the CLIP embeddings), and the rotator walks it. Should a new Favourite be inserted next to its closest match, or trigger a full re-order?
  • Each screen walks its own journey, drawing only wallpapers whose shape fits it, so a portrait screen gets portrait images. Or should the two screens be visually linked and move together?
  • Portrait wallpapers need to enter the Pool. Today the Filters allow one set of ratios. That's the open design question with real options (one Pool with shape tags, or one Pool per screen shape).
  • Day/night chooses from the rotation set by brightness measured from the thumbnail, switched by the clock on Windows and macOS, and by GNOME's own light/dark wallpaper keys on Linux.
  • A change of wallpaper is fire-and-forget. If wallpapi stops, the last wallpaper stays. No autostart, no state kept in the adapter.
  • Every control lives in the web UI (Next, Pause, interval, per-screen settings). The tray is a shortcut to them, because stock Fedora shows no tray.
  • Nothing changes about learning: Batches, Line-ups, the Evidence log, the Refill and scoring stay as they are. The desktop work sits beside them and reads the Library and the embeddings.
  • Packaging: PyInstaller one-folder plus Inno Setup on Windows, built in CI per OS; unsigned for now.

Things I've left out of the diagrams

  • The commands' detail: reset-pool writes, while evaluate and verify-log only read.
  • Thumbnail eviction after a submission, and the rate limiter's internals (ADR 0020).
