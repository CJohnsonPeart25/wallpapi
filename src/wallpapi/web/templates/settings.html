How many Wallhaven favourites a wallpaper needs. Applied here rather than in the search — Wallhaven has no parameter for it.

Pool

How many filtered wallpapers to keep waiting. The background refill fetches at full speed until the pool reaches this, then idles.

Scoring

How far a verdict spreads to wallpapers that look like it. Every score is worked out from the decision log each time a batch is built, so changing these two takes effect on the next batch and nothing has to be rebuilt. Both are starting points rather than tuned numbers.

From 0 to 1. How different two wallpapers can be and still tell you anything about each other — beyond it, a verdict counts for nothing at all.

From 0 to {{ max_similarity_decay }}. How fast a verdict fades with distance. Higher is fussier; 0 counts everything inside the radius equally.

Repeats

From 0 to 1. How likely a wallpaper you have already favourited or liked is to come round again, against one you have not judged at all. 1 shows them as often as anything else; 0 never shows them again while there is something else to show. Wallpapers you only skipped past are not affected, and banned ones never come back whatever this says.

Thumbnails

Megabytes. Thumbnails of wallpapers you have judged are never deleted — history needs them — so this only limits the ones still waiting in the pool. Anything deleted is fetched again the next time it is shown.

{# Downloading the favourites (#14). A form of its own and outside the settings form, because HTML does not nest forms and this posts no fields at all — the operation takes no arguments, which is what makes it safe to press twice. One way only. There is no button anywhere that empties the library: files leave it when a favourite is replaced, and never because the folder and the log were compared. #}

Favourites

Favourites are downloaded to the library folder as you submit each batch, so this is only needed when the folder and your decisions have come apart — you deleted the files, you moved the library, or you brought the database to another machine. It downloads every favourite that has no file and leaves everything else alone. It never deletes anything, and deleting a file yourself never changes your decision log.

{# Mixes (#12). Outside the settings form and not inside it: each row is a form of its own, HTML does not nest forms, and a mix row posts four fields under names every other row posts too — so one big form would send three copies of "unknown" and the server would have to guess. Editing and adding post to the same route. A mix is saved under its name, and whether one was already there is not a question worth asking the user; that also means there is no rename — saving under a new name makes a second mix. No delete control on explore, on refine, or on the active mix. All three are refusals the core service makes anyway, and a page that offers a button which cannot work is a page telling the user something untrue — the same reason history renders no clear control on a row with nothing to clear. #}
